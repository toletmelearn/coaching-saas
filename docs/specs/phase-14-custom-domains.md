# Phase 14: Custom Domains

**Status:** Planned — not implemented. Spec written 2026-10-04 as a planning document; no
application code, migration, route, test or config change accompanies it. Phase 14 is this
feature's canonical slot (`ROADMAP.md` Stage C; `PROJECT_BRIEF.md` §3 — the number was
renumbered twice by drift C11/C12 and has always meant custom domains, never another
feature).

---

## Goal

A tenant can bring their own domain (`physics-institute.com`) alongside their platform
subdomain (`physics.coaching.test`), prove they own it via DNS, and have the platform
serve them there with TLS issued automatically through Caddy's on-demand TLS. Resolution,
tenancy and isolation do not change in spirit: one row in `tenant_domains`, exact-hostname
lookup, fail closed (TENANCY.md "Resolution").

Explicitly out of scope:

- **Wildcard custom domains** (`*.physics-institute.com`) — one domain per row, no
  wildcards, no per-hostname fan-out.
- **More than 3 custom domains per tenant** — 3 is the proposed cap (Assumptions);
  subdomains are platform-minted and don't count toward it.
- **Domain transfer between tenants** — not a supported operation; the owner removes it
  (or the admin does), the new tenant adds and re-verifies it.
- **Email deliverability** (SPF/DKIM/DMARC) for the custom domain — the platform sends no
  mail from tenant domains.
- **Custom domains for the platform itself** — the platform keeps `PLATFORM_DOMAIN`;
  central domains are never claimable (validated against `config('tenancy.central_domains')`).
- **Redirects from the subdomain to the custom domain** — both hostnames keep serving;
  canonical-URL/SEO handling is a later concern.

## Schema

### Existing (Phase 1, unchanged shape)

`tenant_domains` is a **central** table (ARCHITECTURE.md "Central (non-tenant) tables";
`TENANCY.md` central-table exception) — no `tenant_id` scoping issue, no `BelongsToTenant`:
it *describes* tenants. Per `docs/specs/phase-1-tenant-resolution.md` §Tenant Domains Table
it already has:

```
id · tenant_id (FK restrict) · domain (unique, mutator lowercases + strips trailing dot)
· type (DomainType: subdomain | custom) · is_primary · verified_at (nullable) · timestamps
```

`DomainType::Custom` has existed since Phase 1 with no creation code path
(`app/Enums/DomainType.php`), and every subdomain row is minted `verified_at => now()`
(`app/Actions/CreateInstituteAction.php:84-86`, `TenantSeeder` likewise).

### Proposed changes (one migration; not written by this spec)

```
tenant_domains (altered)
+ verification_token   char(32)      — bin2hex(random_bytes(16)); 32 hex chars. Minted
                                       when a custom row is created; regenerated by an
                                       admin force re-verify. Unique.
+ last_checked_at      timestamp null — when the DNS check last ran against this row.
+ last_check_ok        boolean null   — result of that last check (null = never checked).
+ tls_issued_at        timestamp null — set when the Caddy ask endpoint approves this
                                       hostname; the platform's only observable proxy
                                       for "a certificate was actually minted" (see risks).
```

Decisions the prompt asked this spec to settle:

- **`verification_token`** — added; it is the whole proof mechanism.
- **`verification_method`** — **not** added. TXT is the only verification method in v1; a
  column whose every value would be `'txt'` is dead weight. Revisit only if a second
  method is ever designed.
- **`last_verified_at`** — **not** added. Phase 1's `verified_at` *is* the last successful
  verification: force re-verify nulls it, a passing re-check sets it again. Two columns
  would invite disagreement; one cannot.
- **`tls_issued_at`** — added, with the honest caveat that it records ask-approval time,
  not a probe of the certificate itself (Caddy asks immediately before issuing, so a 200
  here means issuance is underway).
- **One shared table vs a new `domain_verifications` table** — **shared table wins.**
  Verification is 1:1 with a domain row; the resolver and the ask endpoint must agree on
  exactly one predicate (a second table creates a second source of truth for "may this
  hostname serve?"); and `UNIQUE(domain)` then blocks cross-tenant claims across *pending
  and verified* states with a single constraint instead of an application check spanning
  two tables. Rejected alternative, documented for a reviewer who forbids touching
  `ResolveTenant`: keep unverified rows in a staging table and insert into `tenant_domains`
  only after verification — zero middleware change, but collision checks and revocation
  then span two tables.
- **Does `ResolveTenant` need a change?** — the *mechanism* needs none, **confirmed**:
  `app/Http/Middleware/ResolveTenant.php:25` already does
  `TenantDomain::query()->where('domain', $host)->first()` and `:28` already `abort(404)`s
  on a miss — exact-hostname lookup serves custom domains as-is, no wildcard logic, no new
  table. One *predicate* addition is required, however, to deliver this spec's mandated 404
  for unverified custom domains (below): a custom row is inserted at "add" time with
  `verified_at = null`, and today's lookup would happily resolve it.

  Proposed single change at `ResolveTenant.php:25`:

  ```php
  TenantDomain::query()
      ->where('domain', $host)
      ->where(fn ($q) => $q->where('type', DomainType::Subdomain)
                           ->orWhereNotNull('verified_at'))
      ->first();
  ```

  Type-based, not a bare `whereNotNull('verified_at')`, so platform-minted subdomains —
  trusted by construction — can never be knocked out by a legacy or factory row missing
  `verified_at`. This is the only edit this phase makes to tenant-resolution code, and it
  is covered by dedicated tests (Required tests §4).

## Behaviour

### Owner add flow

1. Owner opens `/manage/settings/domains`, enters `physics-institute.com`.
2. Validation (all failures are redirect-back 422s with `domains.errors.*` copy):
   - hostname format (ASCII-only regex; the model mutator already lowercases and strips a
     trailing dot);
   - rejects `*.` prefixes (wildcards out of scope), anything under
     `tenant_base_domain`/`platform_domain` (subdomains are platform-minted only), and
     anything in `central_domains` (the platform can never be claimed);
   - rejects a `domain` already present in `tenant_domains` **for any tenant or any
     status** → `errors.taken` (pre-check for the friendly message; `UNIQUE(domain)` is
     the real guarantee);
   - rejects a 4th custom row for this tenant → `errors.cap` (subdomains excluded).
3. Row created: `type = custom`, `is_primary = false`, `verified_at = null`,
   `verification_token` minted. The tenant's subdomain row is untouched; the subdomain
   stays primary.
4. The page shows the two DNS records to add:
   - **Ownership TXT:** host `_coaching-verify.<domain>`, value
     `coaching-verify=<32-hex token>`;
   - **Routing:** `CNAME <domain> → tenants.<PLATFORM_DOMAIN>` (apex: `A <domain> →`
     the configured platform IPs; see Assumptions).

### DNS check — polling design (outlined, not implemented)

- **Seam:** `App\Support\Domains\DnsResolver` — a thin interface with a system
  implementation (`dns_get_record()` + target resolution) and a fake for tests, mirroring
  the `FakeVideoProvider` pattern. **No test ever performs a live DNS query.**
- **Scheduled:** `php artisan domains:verify`, every 5 minutes `->onOneServer()` in
  `routes/console.php` alongside `videos:sync` (`:18`) and `devices:prune` (`:28`). It
  selects custom rows whose `last_checked_at` is older than the cadence (or null), runs
  one check each, writes `last_checked_at`/`last_check_ok`.
- **Manual:** a "Verify now" button (`POST`, throttled like
  `settings/services/test-bunny`'s `throttle:10,60`, `routes/web.php:106`) runs the same
  check inline and reports the result in flash copy.
- **One check evaluates both records.** TXT present *and* matching, **and** a routing
  record present *and* targeting the platform → `verified_at = now()`,
  `last_check_ok = true`. Otherwise `last_check_ok = false` and the flash/UI names the
  reason: "TXT record not found or mismatched" vs "routing record not found" (two distinct
  failure copies — they send the owner to different places in their DNS panel).
- **A failed check never deletes the row and never clears an already-set `verified_at`.**
  Revocation is a human action (admin force re-verify), never a transient DNS hiccup.
  Trade-off pinned in Assumptions and Known limits.

### Status badge (derived, never stored — one helper, `DomainStatus`)

| Badge | Predicate (precedence top-down) |
|---|---|
| `failed` | `last_check_ok === false` (even on a verified row — a re-check that now fails) |
| `live` | `verified_at` set **and** `tls_issued_at` set |
| `verified` | `verified_at` set **and** `tls_issued_at` null |
| `unverified` | `verified_at` null and no failed check recorded |

### TLS — Caddy on-demand and the ask endpoint

- Caddy obtains certificates for unknown hostnames **only** after a database-gated "ask"
  endpoint says yes. This is `SECURITY.md` §"Custom domains and TLS" (line 466) and
  **AGENT_RULES.md invariant 16** (`:66`): *"Caddy 'ask' endpoint approves only verified
  domains — never an open approve-any-hostname."*
- **Contract:** `GET /.well-known/tls-ask?domain=<hostname>`, registered inside the
  central-domain loop (`routes/web.php:55`), **no `->name()`** (P1.1 route:cache gotcha,
  `routes/web.php:59-66`, `RouteRegistrationTest`), `throttle:60,1` per IP.
  - **200 — approve:** a `tenant_domains` row exists for the exact host **and**
    `verified_at IS NOT NULL`. Side effect: `tls_issued_at = now()` if currently null.
  - **404 — deny:** unknown host *or* unverified custom. Uniform status and body — the
    endpoint must not distinguish "never seen" from "not yet verified", so it leaks no
    existence information. Caddy treats any non-2xx as "do not issue".
  - **429 — over budget:** also non-2xx → deny (fail closed under abuse).
  - The ask URL targets a central-domain hostname (whose certificate is managed
    statically, not on-demand), so the ask itself never needs a certificate it is asking
    permission to create.
- **Where the Caddy config lives:** a `Caddyfile` (repo root or deployment fragment) with
  a `on_demand_tls { ask … }` block plus `tls { on_demand }` on the custom-domain site
  matcher. It does **not** exist today (`grep -ri caddy docs/DEPLOY.md` → nothing);
  `docs/DEPLOY.md` gains its section **when the phase is implemented**, not now — and the
  Nginx/Cloudflare topology question is an Unresolved risk below.

### Routing — what actually happens

1. **First HTTPS request after verification, before a certificate exists:** DNS already
   points at the edge; Caddy receives SNI for an unknown hostname → asks → 200 → ACME
   issuance (seconds to a few minutes) → serves. The very first connection may fail once
   or twice while issuance completes; owner copy sets that expectation ("live within
   minutes").
2. **Verified and certified:** `ResolveTenant:25` resolves the row, `TenantContext` is
   set, the tenant's app runs — identical to a subdomain from line 141 of
   `routes/web.php` onward.
3. **Unverified custom domain:** the predicate above excludes the row → `abort(404)` at
   `ResolveTenant:28` — fail closed per TENANCY.md ("If the hostname does not match a row
   in `tenant_domains`, the request is rejected"). Independently, the ask endpoint 404s,
   so no certificate is ever issued for it — both layers refuse.
4. **Unknown hostname:** unchanged 404 (row absent) — no default tenant, ever.
5. **Plain HTTP on port 80:** Caddy's automatic :80 → :443 redirect happens before
   Laravel; for an unverified host the redirect target then fails TLS *and* would 404.
6. **Removing a domain** deletes the row → next request is a 404 on both layers
   immediately (resolver has nothing to find; ask has nothing to approve).

### Admin force re-verify

`POST /admin/institutes/{tenant}/domains/{tenantDomain}/force-reverify`:

- `verified_at = null`, `tls_issued_at = null`, `last_check_* = null`, **new**
  `verification_token`.
- Effect is instant and fail-closed on both layers: ask denies (no renewal for the
  already-issued cert — it goes dark at expiry unless re-proven) and the resolver 404s
  until the owner verifies again with the new TXT value. Deliberate: an admin pressing
  this button is asserting "I no longer trust this proof".
- Writes `AdminAuditLog::record('force_reverify', 'tenant_domain', …)` — Phase 13's
  `admin_audit_logs`, same call shape as `Admin/InstituteController.php:60`.

### Removal

`DELETE /manage/settings/domains/{tenantDomain}` — **idempotent**: the first call deletes
and flashes success; a second call (double-click, stale tab) is the same success no-op,
not a 404/422/500 (invariant: approval-style handlers are idempotent — PROJECT_BRIEF §5
item 12's rule applied to a destructive action). Rows are resolved **within the current
tenant context** (see Routes) — `TenantDomain` is central, so a raw id must never reach
another tenant's row.

## Security

1. **The ask endpoint is never an open approve-any.** It approves iff `tenant_domains`
   has the exact hostname **with `verified_at` set** — `SECURITY.md:466`,
   AGENT_RULES invariant 16 (`AGENT_RULES.md:66`). Uniform 404 for unknown *and*
   unverified (no existence oracle), throttled, central-domain-only. A canary test must
   fail if anyone ever weakens the predicate.
2. **Cross-tenant domain hijacking is blocked three ways:** `UNIQUE(domain)` (DB), a
   friendly pre-check across *all* tenants *and all statuses* (app), and validation
   rejecting platform/central/`*.tenant_base_domain` names. Tenant A can neither add
   tenant B's subdomain nor any domain (pending or verified) already held by tenant B.
   Route-bound ids resolve only inside the caller's tenant context (404 otherwise).
3. **The verification token is unguessable:** `bin2hex(random_bytes(16))` — 32 hex
   chars, the same construction as Phase 8's device id (`phase-8-devices.md` §Registration).
   Unique, never logged, rendered only to the owner (owner-only screen).
4. **No TLS before ownership is proven.** Issuance requires `verified_at`, which requires
   a passing TXT + routing check. There is no admin "approve without check" — the only
   admin lever *removes* trust (force re-verify), never grants it.
5. **Removal is idempotent** — twice-remove is a no-op success, not an error
   (Required tests §5).
6. **Force re-verify is audit-logged** — `AdminAuditLog::record(...)` per Phase 13
   (`admin_audit_logs`), required by AGENT_RULES rule 12 for security-sensitive actions.
7. **Fail closed everywhere:** unverified → 404 (resolver) *and* 404 (ask); revocation
   flips both instantly; unknown host → 404; no default tenant (TENANCY.md:7-10).
8. **Mass-assignment:** `verification_token`, `verified_at`, `tls_issued_at`,
   `last_check_*` are guarded — set only by the controller/command/force action, never
   from request input. Given `TenantDomain::$fillable` already contains `tenant_id`
   (PROJECT_BRIEF §5 gotcha #26), the new controller builds rows explicitly from a
   validated array, `CreateInstituteAction`-style.
9. **DNS failures never auto-revoke** — a transient resolver outage must not 404 a
   live tenant; the human force-re-verify is the fail-closed lever. Trade-off stated in
   Assumptions and Known limits rather than hidden.

## Assumptions

Every decision this plan makes that the implementer must confirm before coding:

- **Verification = TXT *and* routing record.** `verified_at` is set only when both pass;
  TXT alone is not enough (the prompt's three-layer model read strictly). Alternative —
  TXT gates verification, routing failure only warns — rejected: an unreachable domain is
  not a working domain.
- **DNS poll cadence: every 5 minutes**, scheduled `onOneServer()`, plus throttled manual
  Verify-now. No long-polling/websockets.
- **No verification TTL.** The token is a static TXT value — re-checkable forever, so a
  "verification expires at T" concept is deliberately not modeled. Confirm no periodic
  expiry is wanted.
- **Monthly re-check sweep** of already-verified rows: a failure flips the badge to
  `failed` (warning) but does **not** auto-revoke `verified_at`. Availability over
  freshness; Force re-verify is the revocation lever. Confirm the sweep interval.
- **Domain cap: 3 custom domains per tenant** (subdomains excluded).
- **Apex domains:** `A` record accepted as well as `CNAME` (apex cannot CNAME on classic
  DNS; flattening providers behave differently — resolver accepts either against the
  configured target). `www` is a separate row, counting toward the cap.
- **Routing target:** `tenants.<PLATFORM_DOMAIN>` CNAME plus an A-record IP list, both in
  `config('tenancy.php')` (config-only `env()` reads — never `env()` in app code). Exact
  values depend on the topology decision below.
- **Ask endpoint shape:** `GET /.well-known/tls-ask?domain=`, 60/min per IP. Caddy's ask
  URL is ours to choose; confirm path and budget.
- **`tls_issued_at` = approval time** (proxy for issuance; the platform does not probe
  certificates).
- **`ResolveTenant` predicate change is acceptable** (type-or-verified). The
  zero-middleware staging-table alternative exists but was rejected — confirm no reviewer
  objection.
- **No feature flag.** Unlike `LIVE_CLASSES_ENABLED`, there is nothing half-on to
  protect: with no verified rows the ask always denies and the resolver always 404s, so
  an unconfigured install is safe by default. Confirm no `CUSTOM_DOMAINS_ENABLED` wanted.
- **Idempotent remove = 302 success on the second call**, not 404.
- **Owner-only, never staff**, for domain management.
- **On-demand TLS applies to custom hostnames only**; subdomains keep their existing
  static/wildcard certificate path.

## Unresolved risks

- **DNS propagation delay.** Minutes to 48 hours; the owner sees `failed` for records
  that are simply not visible yet. Copy must say "wait and retry" — the check cannot
  distinguish "not propagated" from "wrong value".
- **Certificate issuance rate limits.** Let's Encrypt allows 5 certificates per
  registered domain per week; force-reverify loops or apex+www pairs can burn that. Worse,
  **a failed issuance after a 200 ask is invisible**: `tls_issued_at` is set, the badge
  says `live`, the site is dark. No probe exists (Known limit #1).
- **DNS realities.** Apex CNAME flattening (Cloudflare et al.), split-horizon DNS, and
  providers with slow AXFR-style propagation can make the routing check false-negative;
  the resolver accepts A alternatives but this is inherently fuzzy.
- **Add-and-never-verify.** The pending row occupies `UNIQUE(domain)` forever, blocking
  the rightful owner — even in another tenant — from ever claiming that hostname. Needs
  an eventual prune policy; not in v1 (Known limit #4).
- **Verified, then the domain expires.** A stranger registers the abandoned domain,
  points DNS at the platform: the ask still approves (stale `verified_at`), and
  `ResolveTenant` serves the original tenant's content at the attacker's hostname — a
  phishing wrapper around a real institute. The monthly re-check detects the missing TXT
  and warns but does not revoke (Assumptions), so the residual window lasts until an
  admin acts. The sharpest security edge in this phase; needs a human decision.
- **Deploy topology conflict.** `SECURITY.md` commits to Caddy on-demand TLS, but
  `docs/DEPLOY.md`'s target stack is Nginx (CloudPanel) + Cloudflare Full(strict) +
  wildcard origin certificate, with **zero Caddy mentions today**. Where Caddy runs
  (replacing Nginx? in front? custom hosts only?), what the ask URL is, which IPs the A
  records point at, and whether Cloudflare proxies custom hosts must be settled before
  implementation. `docs/DEPLOY.md` gains its Caddyfile section when the phase ships.
- **Local development has no Caddy** — the TLS half cannot run locally; verification,
  resolver and ask-contract behaviour are fully testable through fakes (same standing
  caveat as Phase 12's JaaS end-to-end). `php artisan local:hosts` will print pending
  custom rows too, which is useful for app-level manual checks.
- **IDN/Unicode domains are rejected** (ASCII-only validation); owners must enter
  punycode themselves. Deliberate v1 simplification, revisit if asked.
